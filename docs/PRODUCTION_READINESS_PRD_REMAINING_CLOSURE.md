# PRD — المتبقي لإغلاق المنظومة وجاهزيتها للإنتاج

الإصدار: 1.0  
التاريخ: 2026-08-02  
النطاق: نظام WAAD TPA — الجاهزية الوظيفية، التقنية، الأمنية، وتجربة المستخدم.  
الغرض: تحويل المتبقي من ملاحظات ومخاطر إلى خطة إغلاق إنتاجية قابلة للتنفيذ والاختبار.

---

## 1. الملخص التنفيذي

المنظومة قطعت شوطاً كبيراً في الانتقال من نظام تطويري متشعب إلى منظومة TPA أكثر تماسكاً: تم تنظيف أجزاء من قواعد التغطية، محرك التغطية، المطالبات، القاموس الطبي، قوائم الأسعار، بوابة مقدم الخدمة، الإعدادات، والسجل الطبي.  

لكن الجاهزية الإنتاجية لا تُقاس فقط بأن الشاشات تعمل؛ بل بأن كل مسار:

- يعطي نتيجة مالية صحيحة.
- يمنع الوصول غير المصرح.
- يعرض رسائل واضحة.
- يتحمل بيانات كبيرة.
- قابل للتتبع والتدقيق.
- يمكن تشغيله واستعادته بثقة.

التقييم الحالي العام بعد آخر إغلاق للإعدادات:

| المحور | الجاهزية التقديرية |
|---|---:|
| الإعدادات العامة وبوابة مقدم الخدمة | 94–96% |
| قواعد التغطية ومحرك التغطية | 90–93% |
| المطالبات والحسابات المالية | 90–94% |
| القاموس الطبي وتنظيم قوائم الأسعار | 88–92% |
| المستفيدون والسجل الطبي | 85–90% |
| مقدمو الخدمة وعقودهم | 87–92% |
| جهات العمل والوثائق | 87–92% |
| الموافقات والمراجعة | 88–92% |
| التقارير المالية والتشغيلية | 82–88% |
| الأمن والصلاحيات والتدقيق | 85–91% |
| الجاهزية العامة للنشر الآمن | 88–92% |

الهدف المطلوب قبل الإنتاج:

- حد أدنى للنشر التجريبي الآمن: 95%.
- حد مستهدف للنشر الإنتاجي المريح: 98–99%.

## 2. تعريف الإغلاق الإنتاجي

يُعتبر القسم مغلقاً إنتاجياً عندما تتحقق الشروط التالية:

1. المتطلبات الوظيفية تعمل من الواجهة والباك إند معاً.
2. لا توجد مسارات قديمة فعالة دون قرار واضح.
3. الأخطاء تظهر للمستخدم برسائل مفهومة.
4. الصلاحيات تمنع الوصول غير المصرح.
5. الحسابات المالية قابلة للتفسير والمراجعة.
6. السجل والتدقيق يحفظان الأثر التشغيلي.
7. توجد اختبارات آلية أو يدوية موثقة للحالات الحرجة.
8. لا توجد بيانات أو إعدادات تدريبية مؤثرة على الإنتاج.

| الأولوية | الوصف | أمثلة |
|---|---|---|
| P0 | مانع إنتاجي، خطر مالي/أمني مباشر | اعتماد مطالبة غير مغطاة، وصول مقدم خدمة لبيانات مرفق آخر |
| P1 | خطر تشغيلي مرتفع | فشل استيراد، تقرير مالي غير مطابق، رسالة خطأ غامضة لمسار حساس |
| P2 | جودة وتجربة مستخدم | تشتت واجهة، نقص عدادات، ضعف فلترة |
| P3 | تحسين لاحق | تحسين chunks، تحسينات شكلية غير مانعة |

# 4. المتبقي حسب الأقسام

## 4.1 إعدادات النظام

### الوضع الحالي

تم إغلاق حزمة مهمة:

- حذف تبويب “قواعد التغطية المالية”.
- إصلاح حفظ `ELIGIBILITY_STRICT_MODE=false`.
- جعل `LOGO_URL` اختيارياً.
- إضافة خيار إظهار/إخفاء مسار الدفعات.
- ربط خيار الموافقات المباشرة بحارس Backend.
- تنظيف ESLint للصفحة.

### المتبقي

| المتطلب | النوع | الأولوية | معيار القبول |
|---|---|---:|---|
| تنفيذ الاختبارات اليدوية الموثقة في `SETTINGS_PRODUCTION_MANUAL_TESTS.md` | وظيفي | P0 | نجاح كل الاختبارات السبعة دون رسائل غامضة |
| التأكد من أن كل خيار في تبويب بوابة مقدم الخدمة يؤثر على الواجهة والـ API | وظيفي/أمني | P0 | تعطيل الخيار يخفي الزر ويرفض API |
| توحيد رسائل نجاح/فشل حفظ الإعدادات | UX | P1 | لا تظهر رسائل إنجليزية للمستخدم النهائي |
| توثيق مفاتيح الإعدادات وFeature Flags | تقني | P2 | ملف مرجعي يوضح المفتاح، الأثر، القيمة الافتراضية |

### اختبار قبول مختصر

- حفظ إعدادات بشعار فارغ.
- تعطيل/تفعيل الاستحقاق الصارم.
- تعطيل البوابة.
- تعطيل المطالبات المباشرة.
- تعطيل الموافقات المباشرة.
- تعطيل الدفعات.

## 4.2 قواعد التغطية ومحرك التغطية

### الوضع الحالي

تم الانتقال إلى تصنيفات طبية موحدة، وقواعد تغطية مفصلة، ومحرك تغطية هو المسؤول الوحيد عن الحسابات المالية: النسبة، السقوف، المرفوض، المتبقي، وعدد المرات والمدة.

### المتبقي

| المتطلب | النوع | الأولوية | معيار القبول |
|---|---|---:|---|
| اختبار شامل لوثيقتي جليانة ومصرف الوحدة | مالي/وظيفي | P0 | كل تصنيف يرجع نسبة وسقف صحيحين حسب السياق |
| اختبار السقوف الزمنية: يوم، أسبوع، شهر، سنة، سنتين، 5 سنوات، مدى الحياة، لكل زيارة | مالي | P0 | المحرك يحتسب الاستخدام ضمن الفترة الصحيحة |
| منع اعتماد مالي لبند غير مغطى إلا بسياسة واضحة | مالي/أمني | P0 | لا يمكن حفظ مطالبة مع بند غير مغطى كمعتمد |
| التأكد من أن السقف العام لا يظهر كسقف منفعة إذا لا يوجد سقف منفعة | مالي/UX | P0 | حقل سقف المنفعة يعرض “-” أو لا سقف |
| اختبار soft delete/restore/hard delete لقواعد التغطية | تقني | P1 | لا حذف نهائي لقاعدة مرتبطة مالياً |
| اختبار الاستيراد الجماعي للقواعد | وظيفي | P1 | ملف صحيح يستورد دون تكرار أو فقدان |
| توثيق مصفوفة التصنيفات الموحدة | تقني | P1 | لا توجد تصنيفات مكررة باسمين مختلفين |

### مخاطر مفتوحة

- أي خطأ في السياق OP/IP يؤدي إلى حساب خاطئ.
- أي تصنيف قديم متبقٍ قد يكسر الربط مع محرك التغطية.

## 4.3 المطالبات والحسابات المالية

### الوضع الحالي

المطالبات تعتمد على محرك التغطية. تم تحسين عرض عدد خدمات السياق، منع اعتماد غير مغطى، رفض بند/مطالبة، وتعلم القاموس من تعديل التصنيف.

### المتبقي

| المتطلب | النوع | الأولوية | معيار القبول |
|---|---|---:|---|
| اختبار إدخال مطالبة OP/IP لكل التصنيفات المعتمدة | مالي | P0 | النسبة والسقف وحصة الشركة والمشترك صحيحة |
| اختبار تغيير السياق بعد اختيار الخدمات | وظيفي/مالي | P0 | الخدمات غير المناسبة للسياق تظهر كتحذير ولا تُعتمد مالياً |
| اختبار رفض بند | وظيفي/تدقيق | P0 | يظهر سبب الرفض ويُستبعد مالياً ويسجل أثره |
| اختبار رفض مطالبة كاملة | وظيفي/مالي | P0 | تحفظ المطالبة مرفوضة بقيم مالية صحيحة |
| منع حفظ/اعتماد مطالبة ببند غير مغطى | أمني/مالي | P0 | الحفظ النهائي يرفض أو يفرض تصحيحاً |
| اختبار تعديل مطالبة معتمدة يدوياً | وظيفي | P1 | مسموح حسب قرارك مع سجل تدقيق واضح |
| ربط تعديل التصنيف بسجل مراجعة القاموس | وظيفي/تعلم | P1 | كل تغيير تصنيف ينتج اقتراح تعلم قابل للاعتماد |
| مقارنة ملخص المطالبة مع التقارير المالية | مالي | P1 | الإجماليات متطابقة في المطالبة والتقرير |

### حالات اختبار حرجة

- بند مغطى 75% بلا سقف.
- بند مغطى بسقف مالي.
- بند مغطى بعدد مرات.
- بند مغطى بسقف زمني.
- بند غير مغطى.
- بند يتجاوز سقف منفعة.
- بند يتجاوز السقف العام.
- مطالبة تحتوي مزيج مغطى/غير مغطى.

## 4.4 القاموس الطبي وتنظيم قوائم الأسعار

### الوضع الحالي

تم دمج فكرة أداة التصنيف داخل المنظومة كـ “القاموس الطبي”، مع تنظيم قوائم الأسعار، دمج التكرارات، نطاق سعري، كود المرفق، حفظ جلسات، تقرير فروقات، وترحيل لعقود مقدمي الخدمة.

### المتبقي

| المتطلب | النوع | الأولوية | معيار القبول |
|---|---|---:|---|
| اختبار دورة كاملة: رفع → تصنيف → مراجعة → حفظ جلسة → فرق → ترحيل | وظيفي | P0 | كل خطوة تحفظ حالة واضحة |
| منع تكرار نفس جلسة قائمة الأسعار لنفس الملف/المصدر دون قرار | تقني/UX | P1 | يظهر تحذير: قائمة موجودة مسبقاً |
| اختبار مجال السعر في الترحيل والمطالبة | مالي | P0 | أقل سعر يظهر افتراضياً وأي تجاوز للمجال يُرفض |
| اختبار اختلاف السعر لنفس الخدمة من نفس المصدر | وظيفي/مالي | P1 | يتحول إلى مجال سعري أو يبقى مفصولاً حسب خيار الدمج |
| اختبار تصدير “مدمج/غير مدمج” بنفس شكل العرض | UX | P1 | يمكن تغيير التصنيف في الحالتين |
| اختبار البحث بكود المرفق واسم الخدمة الأصلي | وظيفي | P1 | البحث يعثر على الخدمة بالكود أو الاسم أو المرادف |
| اختبار تعلم القاموس من تعديل المراجع | وظيفي/تدقيق | P1 | ينتج سجل تغيير قابل للاعتماد أو التراجع |
| توثيق أن القاموس لا يعتمد قراراً مالياً | أمني/مالي | P0 | كل الحسابات تبقى بمحرك التغطية فقط |

### مخاطر مفتوحة

- التكرار من المصدر قد يسبب تضخم عقود إن لم يضبط.
- المجال السعري يحتاج سياسة واضحة عند المطالبة.
- تعلم القاموس يجب أن يكون قابلاً للتراجع.

| اختبار حذف خدمات العقد وانعكاس ذلك على حالة جلسة التصنيف | وظيفي | P1 | الجلسة تعود قابلة للترحيل إذا لم تعد الخدمات موجودة |
| اختبار تحديث أسعار عقد قائم من جلسة مصنفة | مالي/وظيفي | P1 | تقرير فروقات قبل التحديث، ثم تحديث محدد |

## 4.6 بوابة مقدم الخدمة

### الوضع الحالي

بوابة مقدم الخدمة موجودة، وتم ربط بعض الخيارات من الإعدادات بها. بقيت الحاجة لإغلاق السلوك النهائي، المرفقات، والصلاحيات.

### المتبقي

| المتطلب | النوع | الأولوية | معيار القبول |
|---|---|---:|---|
| عزل بيانات كل مقدم خدمة حسب المرفق المرتبط بالمستخدم | أمني | P0 | لا يرى مقدم خدمة بيانات مرفق آخر |
| اختبار مستخدمين مرتبطين بنفس المرفق | أمني/وظيفي | P0 | كلاهما يرى نفس نطاق المرفق فقط |
| اختبار تغيير المرفق المرتبط بالمستخدم | أمني/وظيفي | P1 | يظهر المرفق الجديد بعد تحديث الجلسة/الدخول |
| إظهار اسم المرفق المرتبط في إدارة المستخدمين | UX/إداري | P1 | يظهر عمود مقدم الخدمة/المرفق للمستخدم |
| اختبار تقديم مطالبة مباشرة | وظيفي/مالي | P0 | تمر بمحرك التغطية وتظهر في المراجعة |
| اختبار تقديم موافقة مسبقة مباشرة | وظيفي | P0 | تظهر في مراجعة الموافقات مع مرفقاتها |
| اختبار تعطيل البوابة أو المسارات من الإعدادات | أمني | P0 | الواجهة والـ API يغلقان معاً |

## 4.10 إدارة المستخدمين والصلاحيات

### الوضع الحالي

توجد RBAC، أدوار متعددة، وربط لمستخدمي مقدم الخدمة بالمرفق. ظهرت ملاحظة عن عدم وضوح المرفق المرتبط ورسالة `username required`.

### المتبقي

| المتطلب | النوع | الأولوية | معيار القبول |
|---|---|---:|---|
| إظهار المرفق المرتبط بمستخدم مقدم الخدمة في القائمة | UX/إداري | P1 | عمود واضح باسم المرفق |
| إصلاح حفظ المستخدم عند تغيير المرفق دون خطأ username | وظيفي | P0 | الحفظ لا يطلب username إذا لم يتغير |
| منع مستخدم مقدم الخدمة من ربطه بأكثر من مرفق دون سياسة | أمني | P1 | سياسة واضحة في UI وBackend |
| مراجعة صلاحيات كل دور | أمني | P0 | لا دور يرى أو يعدل خارج صلاحياته |
| سجل تدقيق لتغيير الأدوار والمرفق | أمني/تدقيق | P1 | كل تغيير يسجل من/إلى ومن قام به |
| اختبار تعطيل مستخدم مقدم خدمة | أمني | P0 | لا يستطيع الدخول أو استخدام token قديم |

# 5. خطة الإغلاق المقترحة

## المرحلة 1 — إغلاق P0 المالي والأمني

المدة التقديرية: 3–5 أيام عمل مركزة.

الأعمال:

1. تنفيذ اختبارات إعدادات النظام اليدوية.
2. اختبار محرك التغطية والمطالبات لكل الحالات المالية.
3. اختبار عزل مقدم الخدمة.
4. اختبار حالات المستفيد والاستحقاق.
5. اختبار migrations على قاعدة نظيفة ومحلية.

مخرج المرحلة:

- لا يوجد مسار يسمح بحساب مالي خاطئ.
- لا يوجد مقدم خدمة يرى بيانات غيره.
- لا يوجد endpoint حساس بلا guard.

## المرحلة 2 — إغلاق P1 التشغيلي

المدة التقديرية: 4–7 أيام.

الأعمال:

1. إغلاق دورة القاموس وقوائم الأسعار كاملة.
2. إغلاق الموافقات والمرفقات والمراجعة.
3. إغلاق تقارير المطالبات والموافقات.
4. إغلاق إدارة المستخدمين وربط المرفق.
5. تحسين رسائل الأخطاء التشغيلية.

مخرج المرحلة:

- دورة العمل اليومية تعمل: مستفيد → زيارة/موافقة/مطالبة → مراجعة → تقرير.

## المرحلة 3 — إغلاق P2 الجودة والتجربة

المدة التقديرية: 3–5 أيام.

الأعمال:

1. توحيد الهوية البصرية للشاشات المتبقية.
2. تحسين scroll والارتفاعات.
3. اعتماد مكون المستندات العام.
4. تحسين فلاتر وعدادات التقارير.
5. توثيق المستخدم النهائي المختصر.

مخرج المرحلة:

- تجربة مستخدم مستقرة وواضحة، لا تشعر بأنها أجزاء مركبة من أكثر من نظام.

## المرحلة 4 — اختبار قبول إنتاجي UAT

المدة التقديرية: 2–4 أيام.

الأعمال:

1. تشغيل يوم عمل كامل ببيانات تدريبية قريبة من الواقع.
2. إدخال 20–50 مطالبة متنوعة.
3. إدخال 10 موافقات مسبقة.
4. استيراد قائمة أسعار.
5. توليد تقارير مالية.
6. مراجعة logs والأداء.

مخرج المرحلة:

- قرار Go/No-Go للنشر.

# 6. معايير Go / No-Go

## Go — مسموح بالنشر

- كل P0 مغلقة.
- لا توجد أخطاء 500 في المسارات الحرجة.
- لا توجد رسائل تقنية للمستخدم النهائي في السيناريوهات اليومية.
- محرك التغطية يعطي نتائج متطابقة مع الاختبارات اليدوية.
- صلاحيات مقدم الخدمة معزولة.
- قاعدة البيانات تعمل migrations على بيئة نظيفة.
- يوجد backup/restore مجرب.

## No-Go — لا تنشر

- أي مطالبة غير مغطاة يمكن اعتمادها مالياً دون قرار واضح.
- أي مقدم خدمة يرى بيانات مرفق آخر.
- أي تقرير مالي لا يطابق تفاصيل المطالبات.
- أي migration يمنع إقلاع التطبيق.
- أي شاشة حرجة تفشل بـ 500 عند الاستخدام الطبيعي.

# 9. القرار الهندسي المقترح

المنظومة قابلة للوصول إلى مستوى إنتاجي جيد جداً، لكن لا أنصح بنشرها كإنتاج كامل قبل:

1. إغلاق P0 بالكامل.
2. تنفيذ UAT موثق.
3. اختبار backup/restore.
4. تشغيل مراقبة logs للأسبوع الأول.
5. تجميد التغييرات الكبيرة أثناء الاختبار، والاكتفاء بإصلاحات P0/P1.

النهج الأنسب الآن:

- لا نفتح ميزات جديدة.
- نغلق المتبقي حسب P0 ثم P1.
- نعتبر كل تعديل جديد خارج القائمة “تغيير نطاق” يحتاج قراراً.
