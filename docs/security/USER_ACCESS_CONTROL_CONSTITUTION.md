# دستور إدارة المستخدمين والأدوار والصلاحيات

## القرار المعماري

- لكل مستخدم دور أساسي واحد يحدد قالب العمل، وليس صلاحياته النهائية.
- الصلاحيات الفعلية = صلاحيات قالب الدور + المنح الشخصي - السحب الشخصي.
- السحب الصريح له الأولوية على التوريث.
- امتلاك الصلاحية لا يمنح الوصول لكل البيانات؛ يجب اجتماع الصلاحية مع نطاق البيانات.
- النطاق لا يمنح صلاحية عملية. مثال: موظف مقدم الخدمة قد يرى مستفيداً مسموحاً له، ولا يملك بذلك تصدير السجل المالي.
- لا تُقبل قيمة `null` بمعنى «كل الجهات». النطاق إما عالمي صريح أو مجموعة صريحة أو مرفوض.
- لا يغيّر المستخدم صلاحياته، ولا يمنح المفوّض صلاحية لا يملكها.
- كل تغيير يحتاج سبباً، وسجل التدقيق لا يقبل التعديل أو الحذف.
- تغيير الدور أو النطاق أو الصلاحيات يسحب كل جلسات المستخدم فوراً.
- الواجهة للاكتشاف والشرح؛ الخادم وقاعدة البيانات هما جهة الإنفاذ.

## تجربة الاستخدام المعتمدة

المعالج يتكون من أربع خطوات، بنفس هوية وعد (أخضر مزرق، كحلي، خلفية فاتحة):

1. **الدور الأساسي:** بطاقة لكل دور، وصف موجز، وعدد الصلاحيات الموروثة.
2. **نطاق الوصول:** جهة عمل أو مقدم خدمة وفق الدور، ولا تظهر حقول لا تخص الدور.
3. **الصلاحيات الفعلية:** جدول مصنف يوضح المصدر (الدور/منح/سحب)، مع بحث ومرشحات. الصلاحيات الحساسة تحمل تحذيراً.
4. **المراجعة والتأكيد:** ملخص ما سيُمنح وما سيُسحب، أثر النطاق، سبب إلزامي، وتنبيه بسحب الجلسات.

لا تُعرض مفاتيح تقنية للمستخدم، ولا يُطلب منه فهم `@PreAuthorize` أو أسماء الجداول.

## خطة الإغلاق

### المرحلة 1 — العقد والقاعدة

- قاموس صلاحيات واحد ثابت الرموز.
- جداول قوالب الأدوار والاستثناءات والتدقيق.
- حساب موحد للصلاحيات الفعلية.
- منع التصعيد، التعديل الذاتي، وتعطيل آخر مدير قادر على الاسترداد.
- هجرة مفاتيح `can_view_*` القديمة إلى الاستثناءات ثم حذفها في هجرة لاحقة.

### المرحلة 2 — إدارة المستخدم

- API للمعاينة قبل الحفظ يعيد الفرق الفعلي.
- إنشاء/تعديل ذري للدور والنطاق والاستثناءات.
- سحب الجلسات بعد أي تغيير أمني.
- إدارة قوالب الأدوار بعملية منفصلة عن المستخدمين.
- نافذة سجل تدقيق تعرض مَن غيّر ماذا ولماذا ومتى.

### المرحلة 3 — المعالج البصري

- تطبيق الخطوات الأربع وحالات التحميل/الفشل/عدم وجود نطاق.
- عدم استخدام `window.confirm` أو `window.prompt`.
- إخفاء/تعطيل العمليات بحسب capabilities مع بقاء الخادم حارساً.
- اختبار RTL لكل خطوة واختبار متصفح للإنشاء والتعديل والسحب.

### المرحلة 4 — ترحيل الأقسام

تُنقل الأقسام واحداً واحداً: المستفيدون، المطالبات، الموافقات، مقدمو الخدمة، جهات العمل، العقود والأسعار، المنافع، التسويات، التقارير، الإعدادات. لكل endpoint يلزم:

- capability للعملية؛
- scope للبيانات؛
- اختبار سماح واختبار رفض عابر للنطاق؛
- إزالة الحارس القائم فقط بعد ثبوت التكافؤ.

### المرحلة 5 — إزالة الإرث وبوابة الإنتاج

- لا استعمال مباشر لـ`hasRole` خارج طبقة توافق موثقة.
- لا قراءة لأعمدة `can_view_*`.
- لا endpoint إداري بلا capability مصنف.
- اختبارات PostgreSQL للهجرات والذرية والتزامن والتدقيق.
- مصفوفة أدوار × أقسام × عمليات، واختبار عقد آلي لها.
- دورة متصفح لكل دور، بما فيها تغيير الصلاحية أثناء جلسة مفتوحة.
- فحص أداء لقائمة المستخدمين وسجل التدقيق.

## تعريف الإغلاق 100%

لا يُعلن الإغلاق لمجرد نجاح البناء. يلزم معاً: اكتمال ترحيل جميع المسارات، صفر حارس قديم غير موثق، نجاح مصفوفة السماح/الرفض، نجاح الهجرات على schema قديم ذي بيانات، نجاح دورة المتصفح، وعدم وجود عيب P0/P1 مفتوح. أي بند ناقص يعني أن الملف غير مغلق.
